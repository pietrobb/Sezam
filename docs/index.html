Introduction

Sezam is an encrypted personal and corporate credential vault for passwords, access credentials, SSH keys, API tokens, and sensitive notes. It features a hierarchical tree structure, granular access control (personal, corporate, and AI agents), full-text search, and a self-hosted server for team sharing.

What it solves

  • Personal use — replaces plain text files. One vault, one master password, instant access.
  • Corporate use — replaces credential sharing over messaging apps. Admin sets access, colleagues see only what they should, via web. The server never sees content.
  • AI agents — Claude Code and other agents access credentials via MCP with an approval flow. The agent never receives raw keys — the desktop broker performs the operation on its behalf.

What it is NOT

  • Not a cloud subscription service
  • Not an enterprise solution for thousands of users (handles teams of 2–100 people)
  • Forgotten password = data loss (by design, no password reset for personal vaults)
  • Device loss does not mean data loss — password-based recovery can download keys from the server
  • Corporate vaults have an org-level break-glass mechanism (Shamir's Secret Sharing)

Quick Start

Get up and running in under a minute.

1. Install

There are no release packages yet, and the names sezam and sezam-sync-core on PyPI are not ours: install from a clone (Python 3.11+ and a Rust toolchain for the shared sync core).

git clone https://github.com/pietrobb/Sezam.git
cd Sezam
python -m pip install ./core/py
python -m pip install -e .

For GUI support (PySide6):

python -m pip install -e ".[gui]"

For KeePass import support:

python -m pip install -e ".[import]"

2. Create a vault

sezam init

This runs the first-run wizard:

  1. Prompts for a master password (with strength indicator)
  2. Benchmarks Argon2id for ~1 second on your hardware
  3. Generates Ed25519 + X25519 key pairs
  4. Creates the vault at ~/.sezam/sezam.db
WARNING: Forgotten password = permanent data loss There is no password recovery for personal vaults. Write down your master password and store it in a safe place.

3. Basic usage

# Unlock vault (starts a session)
sezam unlock

# Create an entry
sezam set servers/hetzner/ssh -f host -v 192.168.1.1
sezam set servers/hetzner/ssh -f password -v 's3cret!' -s

# Retrieve a password (copy to clipboard, auto-clear 15s)
sezam get servers/hetzner/ssh -f password --clip

# Search entries
sezam search "hetzner"

# List vault tree
sezam list

# Generate a strong password
sezam generate --length 24 --symbols

# Lock when done
sezam lock

4. Custom vault path

By default the vault lives at ~/.sezam. Override with the SEZAM_VAULT environment variable:

export SEZAM_VAULT=/path/to/my/vault
sezam init --path /path/to/my/vault

Security Model

Content-blind server

The server is content-blind — it stores only encrypted blobs and never sees plaintext content.

Server sees (plain text)Server does NOT see (encrypted)
Number of objectsNode and entry names
Object type (node/entry/dek/envelope)Tier values
Tree topology (parent_ref)Content timestamps
Object ownership (owner_id)Field values (passwords, keys)
Sync timestamps (modified_at)Field keys (“username”, “password”)
Encrypted blob sizesTags
Audit record contents
Not “zero-knowledge” The server sees graph topology and activity patterns. This is a deliberate compromise for efficient synchronization. The term “content-blind” accurately describes what the server cannot see: content, names, tiers, and sensitive metadata.

Identity and keys — two pairs per user

Each user has two separate key pairs:

Ed25519 — SIGNING pair (auth + audit) Private: signing_sk (encrypted with master password) Public: signing_pk (stored on server) Usage: server auth (challenge-response), audit log signatures, sync integrity X25519 — ENCRYPTION pair (envelope encryption) Private: encryption_sk (encrypted with master password) Public: encryption_pk (stored on server) Usage: NaCl crypto_box for DEK envelopes

Why two pairs: X25519 is Diffie-Hellman key agreement — cannot sign. Ed25519 is a signature scheme — cannot encrypt. Separate pairs eliminate cross-protocol risk.

Fingerprint: SHA-256(signing_pk || encryption_pk). The GUI displays three modes:

  • Visual (daily use): identicon generated from fingerprint hash
  • Word-based (TOFU onboarding): 4 BIP39-style words covering 44 bits of entropy
  • Full hex (technical): all 64 hex characters for complete verification

KEK/DEK key hierarchy

Master Password (UTF-8) | v Argon2id(password, salt, time=3, mem=256MB, par=4) | v Root KEK (Key Encryption Key) — 256-bit | +-- Root DEK (scope='root') -- encrypts root node and top-level nodes +-- Folder DEK "servers" -- encrypts entries in servers/ +-- Folder DEK "financial" -- encrypts entries in financial/ +-- Audit DEK (scope='audit') -- encrypts audit log details (separate) +-- ...

Rules:

  • Root KEK unlocks individual DEKs. It never encrypts data directly.
  • Granularity is per-folder. Entry metadata is encrypted with its parent folder's DEK.
  • Tier 2 entries have a separate DEK that MCP agents physically cannot access.
  • Audit DEK is independently versioned — master password changes do not affect the audit chain.
  • Key material in Python uses bytearray with explicit zeroing after lock (best-effort, documented Python GC limitation).

Envelope encryption (multi-user)

When granting access to a folder, the admin wraps the folder's DEK using NaCl crypto_box (authenticated) with the recipient's X25519 public key:

Folder DEK for "clients/auto-moto"
    +-- wrapped via crypto_box(admin_encryption_pk, admin_encryption_sk -> recipient) -> envelope
    |   (authenticated: recipient knows who created the envelope)

Access revocation triggers a mandatory re-key:

  1. Admin revokes user access
  2. New DEK is generated for the affected branch
  3. All entries re-encrypted with the new DEK (single SQLite transaction)
  4. New envelopes created for remaining users
  5. Old DEK archived, wrapped by the new DEK (chain wrapping)

Server authentication — Ed25519 challenge-response

1. Client -> Server: username
2. Server -> Client: challenge = random(32B) + server_timestamp
3. Client: refuses a challenge that is not 40 bytes;
   signature = Ed25519_sign(signing_sk, "sezam-auth-challenge-signature-v1" || challenge)
4. Client -> Server: signature
5. Server: Ed25519_verify(signing_pk, "sezam-auth-challenge-signature-v1" || challenge, signature)
6. Server: verify timestamp is max 30s old (replay protection)
7. Server: mark challenge as "spent" (nonce tracking)
8. Server -> Client: JWT (alg=EdDSA, expiry=1h)

Security guarantees

  1. Content-blind server — no content, names, tiers, or values visible to server
  2. No plain text on disk — never, not even temp files or search indexes
  3. Memory hygiene — best-effort zeroing (bytearray + explicit wipe)
  4. Atomic writes — write to tmp, then rename
  5. Clipboard discipline — auto-clear after 15s with warning about clipboard managers
  6. Fail closed — on error: lock, reveal nothing
  7. Tamper-evident audit — Ed25519 signatures, Merkle DAG for offline fork handling
  8. No telemetry
  9. No personal recovery by design — org break-glass exists for corporate vaults
  10. Padding — blobs padded to nearest power of 2 (random fill, not zero)

CLI Reference

All commands are invoked via the sezam entry point. The vault path defaults to ~/.sezam (override with SEZAM_VAULT env var).

sezam init

Create a new vault. Runs the first-run wizard: prompts for master password, benchmarks Argon2id, generates key pairs, creates sezam.db.

sezam init [--path /custom/path]

sezam unlock

Unlock the vault and start a session. The session persists until sezam lock is called.

sezam unlock

sezam lock

Lock the vault and end the current session. Zeroes key material from memory.

sezam lock

Multi-user & Sharing

Invitation and onboarding flow

  1. Admin creates invitation — desktop app generates a 128-bit random token (72h expiry, one-time use)
  2. Colleague opens link — “Set up your Sezam password”
  3. Browser generates key pairs — Ed25519 + X25519 (or desktop client generates them)
  4. Registration — POST /api/users/register with invitation token + public keys. Returns onboarding JWT (15min)
  5. Keypair upload — PUT /api/me/keypair with encrypted private keys (wrapped by KEK from Argon2id)
  6. Optional backup — download .sezam-key file as offline fallback
  7. Waiting for approval — “Waiting for administrator approval” (polling or SSE)
  8. Admin verification — admin verifies the colleague's fingerprint (in person or by phone), approves, assigns branches
  9. Access granted — colleague receives notification and can see assigned branches

TOFU (Trust On First Use)

Public key authenticity uses the TOFU model (like SSH known_hosts):

  • When adding a colleague, the admin verifies the fingerprint displayed in the GUI
  • The server cannot substitute a public key without the admin seeing the fingerprint change
  • GUI shows a warning if a key changes (MITM detection)
  • Local key cache stores {user_id: (signing_pk, encryption_pk, fingerprint)} — eliminates server dependency for crypto_box operations

Access levels

Pull model

The server sends all vault_objects to every client (the entire vault). Each client locally filters by which DEKs it can unlock via its envelopes. Objects without a matching DEK are unusable encrypted blobs.

Why full pull? This makes the server truly content-blind — it does not need to know who has access to what (except for write ACL). For 2–15 users with thousands of entries, the bandwidth is hundreds of KB, which is negligible.

Sync Protocol

Overview

Sezam uses an offline-first, explicit push/pull model. The local vault is the primary source. Synchronization is delta-based (only changed objects).

Delta push

1. Client collects objects where is_dirty = 1
2. POST /api/sync {objects: [{id, version, payload, payload_hash, signature}]}
   - signature = Ed25519_sign(signing_sk, canonical_signed_data)
3. Server processes each object in a transaction:
   a) Check write_acl (admin exempt)
   b) server.version < client.version -> accept, assign commit_seq
   c) Same version + same payload_hash -> accept (idempotent retry)
   d) Same version + different payload_hash -> 409 Conflict
   e) server.version > client.version -> 409 Conflict
4. Response: {accepted: [{id, commit_seq}], conflicts: [{id, ...}]}
5. Client: accepted -> is_dirty = 0. Conflicts -> stay dirty, GUI shows diff

Delta pull

1. GET /api/sync?since_commit_seq={last_known_commit_seq}
2. Server returns objects where commit_seq > since_commit_seq
3. Client for each object:
   a) Verify client_signature via author's signing_pk
      (invalid signature = REJECTED, fabricated by server)
   b) server.version > local.version -> accept (newer)
   c) Same version + different payload_hash -> ERROR (equivocation)
   d) server.version < local.version -> ignore (stale)
4. Tombstones: verify signature + author had write_acl -> mark deleted
5. Update last_known_commit_seq = max(commit_seq from response)

Conflict resolution

When a conflict occurs (same version, different content), the recommended merge strategy is:

  • Download the server version and decrypt both local and remote
  • Compare at the individual field level (not the entire blob)
  • If different fields were changed, auto-merge by taking the newer value for each field
  • If the same field was changed, prompt the user for manual resolution

Rollback protection

The client maintains a sync checkpoint (encrypted, in vault_meta):

{
  "last_sync_seq": 42,
  "state_hash": "SHA-256(sorted_objects(id || version || SHA-256(payload)))",
  "timestamp": 1710764400000
}

Detects: rollback (lower commit_seq), silent payload changes, equivocation (same version, different payload).

Tombstone GC

Deleted objects (is_deleted=1) are physically removed after 90 days. The audit log retains a signed record of the deletion.

If a client comes back after 90+ days offline with since_commit_seq < gc_floor_seq, the server returns 410 Gone, requiring a full resync. The GUI warns the user and offers to export unsynchronized changes before overwriting.

Idempotent retry

On push retry, the client sends the exact same encrypted blob (from push cache), not a re-encryption. Re-encrypting would produce a different nonce, different ciphertext, different payload_hash, and the server would return 409 instead of OK.

Atomic re-key batches

When a push contains re-key objects (new DEK + re-encrypted entries + new envelopes + tombstoned old envelopes), the client sets atomic_batch: true. The server processes the entire batch in a single database transaction (all-or-nothing).

MCP Integration

Sezam exposes vault tools via the Model Context Protocol (MCP) for AI agents like Claude Code. The MCP server runs as part of the desktop app process.

MCP never gets raw keys or secrets The desktop vault process acts as a broker. It decrypts, performs the operation, returns only the result, and zeroes the key material.

Approval flow

  • Approvals are in-memory only (not persisted). Process restart clears all approvals
  • Default TTL: 5 minutes per approval
  • Single-use: one read, then the approval expires
  • Timeout: 60 seconds to get approval, then denied

Authentication

The MCP server communicates via Unix socket / named pipe with filesystem permissions. Only processes with socket access can call tools. Optionally, a per-session API token is generated at startup.

When vault is locked

All tool calls return {"status": "vault_locked"}. The agent should instruct the user to unlock the vault in the desktop app.

Crypto on mobile

The mobile app uses the same cryptographic primitives as desktop:

  • Argon2id with mobile-adapted parameters: time=2, mem=128MB (auto-detected based on available memory)
  • libsodium via native bindings for AEAD, crypto_box, and Ed25519
Hard floor The mobile client never accepts Argon2id parameters lower than time=2, mem=64MB, even if the server sends weaker parameters.

TOTP support

TOTP seeds are stored as a field with type totp in entry data:

{"key": "totp_secret", "value": "JBSWY3DPEHPK3PXP", "sensitive": true, "field_type": "totp"}

The GUI shows a countdown circular indicator (30s). If less than 5 seconds remain, it waits for the next code before copying. KeePass and Bitwarden imports automatically detect TOTP seeds.

Watchtower

Watchtower scans your vault and reports password security issues. It runs locally — no data leaves your device.

Issue types

TypeSeverityDescription
weakCriticalPassword scores 0–1 on strength meter (low entropy)
weakWarningPassword scores 2 (moderate) — consider strengthening
duplicateWarningSame password used across multiple entries
oldInfoPassword not changed for more than 365 days

How it works

  • Scans all entries with sensitive: true fields
  • Checks password strength using entropy estimation
  • Detects duplicates via SHA-256 comparison (never logs actual passwords)
  • Flags passwords older than 1 year based on modified_at timestamp
  • Results are sorted by severity: critical first, then warning, then info

Summary output

{
  "total": 12,
  "critical": 3,
  "warning": 5,
  "info": 4,
  "by_type": {
    "weak": 5,
    "duplicate": 4,
    "old": 3
  }
}
Privacy Watchtower runs entirely offline. Password values are hashed in memory for duplicate detection and immediately discarded. No data is sent to external services.

Security Best Practices

Master password

  • Use a strong master password with at least 80 bits of entropy (the generator's “Strong” rating)
  • Consider a 5-word passphrase: sezam generate --passphrase --words 5
  • Never reuse your master password for any other service
  • Write it down and store the paper in a physical safe (for personal vaults)
  • For corporate vaults, set up Shamir's Secret Sharing recovery (3-of-5 recommended)

Backup

  • Regularly export encrypted backups: sezam export backup.db
  • Store backups in a separate physical location
  • The backup is a copy of sezam.db — it is still encrypted with your master password
  • Test your backups periodically by restoring to a temporary location

The .sezam-key file

  • This file is an offline fallback for recovering your private keys
  • It is encrypted with your KEK (derived from your master password)
  • Store it on a USB drive in a safe, or print the recovery sheet
  • If you lose all devices and do not have this file, you can still recover via password-based recovery (Path B) if the server has your encrypted keypair
  • Never store .sezam-key on the same device as your vault — that defeats the purpose

General recommendations

  • Keep the desktop app updated for the latest security patches
  • Use auto-lock (default: 15 minutes of inactivity)
  • Be aware that clipboard managers may retain copied passwords — the auto-clear protects the system clipboard only
  • Verify colleague fingerprints in person during onboarding (TOFU)
  • Run Watchtower periodically to find weak, duplicate, or old passwords
  • Review the audit log for unexpected access patterns
  • For the server: use HTTPS in production, set strong SEZAM_HMAC_SECRET, restrict CORS origins
